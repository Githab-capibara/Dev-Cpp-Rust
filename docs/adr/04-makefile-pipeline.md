# 04. Собираем через Makefile и `make` в фоновом джобе

- **Status:** Accepted
- **Date:** 2026-11-23
- **Deciders:** @Githab-capibara
- **Related:** [08. Стримим вывод программы через тот же пайплайн](08-build-and-run-streaming.md)

## Context

Dev-C++ не вызывает компилятор напрямую: он пишет `Makefile.win` и запускает
`make`. Это даёт инкрементальность, параллельность и ровно ту командную строку,
которую пользователь видит в логе. На Linux эквивалент — `Makefile` + GNU make.

## Decision

**Повторяем схему:** `makefile::write(project)` пишет Makefile (C и C++
юниты, `-O2`, debug-флаги, объектники в `obj/`, бинарник в `bin/`), затем
`build::start` запускает `make -f Makefile -j <N>` в отдельном потоке.
stdout и stderr построчно читаются двумя дочерними потоками и уходят в канал
как `BuildMessage::Line` (+ `Diagnostic`, если строка парсится парсером
диагностик). Джоб отменяем (`cancel`) через SIGTERM по pid.

## Consequences

- **Easier:** инкрементальная сборка, параллельные ядра, командная строка
  читается в логе, пользователь может позвать `make` вручную; GUI не
  блокируется.
- **Harder:** нужен парсер вывода make+gcc (см. `diagnostics.rs`); Windows
  совместимость Makefile'а из оригинала не переносим (мы только Linux).
- **Given up:** ничего.
- **Migration:** n/a.

## Alternatives considered

- **Прямой вызов `cc` через `cc`-крейт:** быстрее на пустом проекте, но
  теряет инкрементальность, лог и привычный Dev-C++ workflow.
- **Полный clang-driver-режим (если доступен clang):** оставлен на потом;
  детект тулчейна уже поддерживает gcc/clang-пути.
